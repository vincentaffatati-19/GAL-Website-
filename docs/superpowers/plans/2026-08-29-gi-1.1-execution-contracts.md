# GI-1.1 Shared Execution Contracts

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement the focused GI-1.1 plans. This file defines conventions shared by all of them.

**Goal:** Eliminate implementation ambiguity across the five GI-1.1 focused plans by fixing repository setup, migration naming, test helper, RLS-test, Node-module, and commit conventions.

**Architecture:** The repository is currently a static website and has no `supabase/`, package manager, or application build system. GI-1.1 adds Supabase migrations/tests and uses Node’s built-in test runner for pure JavaScript modules so no package dependency is required merely to test deterministic adapters.

**Tech Stack:** Supabase CLI, PostgreSQL 17, pgTAP, Node built-in `node:test`, ES modules (`.mjs`), Git.

**Spec:** `docs/superpowers/specs/2026-08-28-golfer-intelligence-data-model-v1.1-design.md`

## Global Constraints

- Do not introduce npm dependencies unless a focused task proves they are necessary.
- Do not add a framework rewrite to the static website.
- Database migrations are timestamp-ordered SQL files under `supabase/migrations/`.
- Database acceptance tests are SQL under `supabase/tests/`.
- Pure JS tests are `.test.mjs` and run with `node --test`.
- All synthetic test users/data are non-personal.
- Never use service-role secrets in browser code or committed files.
- No production database mutation while executing these plans.

## Contract 3: Common SQL column conventions

Use these exact physical conventions unless an existing table already requires compatibility:

```sql
id uuid primary key default gen_random_uuid(),
created_at timestamptz not null default now()
```

Stable public/audit IDs use existing GAL helper style when available:

```sql
<entity>_id text not null unique default gal_public_id('GAL-XXX')
```

Confidence:

```sql
confidence numeric not null check (confidence >= 0 and confidence <= 1)
```

Scores:

```sql
fit_score numeric check (fit_score >= 0 and fit_score <= 100)
```

Currency for new columns:

```sql
currency char(3)
```

Ownership FK:

```sql
user_id uuid not null references public.gal_users(id)
```

Use `timestamptz` for all operational timestamps.

## Contract 4: RLS pattern for direct golfer ownership

For a golfer-readable table with direct `user_id` ownership:

```sql
alter table public.<table_name> enable row level security;

grant select on public.<table_name> to authenticated;

create policy <table_name>_self_select
on public.<table_name>
for select
to authenticated
using (user_id = public.gal_current_user_id());
```

For golfer INSERT where allowed:

```sql
grant insert on public.<table_name> to authenticated;

create policy <table_name>_self_insert
on public.<table_name>
for insert
to authenticated
with check (user_id = public.gal_current_user_id());
```

For UPDATE where explicitly allowed:

```sql
grant update on public.<table_name> to authenticated;

create policy <table_name>_self_update
on public.<table_name>
for update
to authenticated
using (user_id = public.gal_current_user_id())
with check (user_id = public.gal_current_user_id());
```

Append-only tables do **not** receive authenticated UPDATE/DELETE grants or policies.

## Contract 5: Synthetic auth/RLS test strategy

Use test-only synthetic UUIDs and claims. A helper file `supabase/tests/helpers/gi11_test_helpers.sql` should define or document the project-compatible mechanism to set JWT claims for authenticated test sessions. The intended behavioral pattern is:

```sql
-- service/setup phase: insert synthetic auth/GAL users through the approved test fixture mechanism
-- authenticated phase A: set auth.uid() to synthetic user A
-- assert A can access A and cannot access B
-- authenticated phase B: set auth.uid() to synthetic user B
-- assert reciprocal isolation
```

The exact Supabase-local auth fixture mechanism must follow the CLI/runtime version in the isolated worktree; do not alter production auth tables. If direct `auth.users` fixture insertion is supported in the local test database, use deterministic synthetic UUIDs and clean them through transaction rollback.

Every RLS test file must wrap fixture work:

```sql
begin;
select plan(<exact assertion count>);
-- assertions
select * from finish();
rollback;
```

## Contract 6: pgTAP assertion style

Structural tests use explicit assertions such as:

```sql
select has_table('public', 'gal_fact_catalog', 'gal_fact_catalog exists');
select has_column('public', 'gal_profile_facts', 'value_state', 'profile facts expose value_state');
select col_is_pk('public', 'gal_fact_catalog', 'id', 'fact catalog id is primary key');
```

Behavioral tests prefer SQL that performs the operation and then uses `is()`, `ok()`, `results_eq()`, or `throws_ok()` with the exact expected outcome.

Example append-only denial:

```sql
select throws_ok(
  $$ update public.gal_profile_fact_history set source_detail = 'tampered' where id = '<fixture-id>' $$,
  null,
  'normal golfer cannot rewrite fact history'
);
```

When a test relies on RLS, execute under the authenticated synthetic-user context rather than a service role that bypasses RLS.

## Contract 7: JavaScript module style

Pure deterministic modules are ES modules and export named functions.

Example:

```js
export function resolveCurrentFact(candidates, rule) {
  // deterministic implementation
}
```

Tests use built-in Node APIs only:

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { resolveCurrentFact } from './intelligence-state-builder.mjs';

test('fresh verified external handicap outranks stale declaration', () => {
  const result = resolveCurrentFact(/* fixture */);
  assert.equal(result.value, 10.9);
});
```

Run:

```bash
node --test tests/gi11/*.test.mjs tests/gi11/**/*.test.mjs
```

If the shell does not expand `**`, run `node --test tests/gi11` or enumerate test directories explicitly.

Browser modules receive only public Supabase configuration and authenticated session tokens. They must never import or embed:

```text

```

All trusted writes for derived/system tables happen server-side or through narrowly reviewed RPCs that enforce ownership and allowed transitions.

## Contract 9: Deterministic scoring hash

Recommendation determinism fixtures serialize a canonical object:

```js
const canonical = {
  eligibility: items.map(({ productId, eligibilityStatus, exclusionReason }) => ({ productId, eligibilityStatus, exclusionReason })),
  ranking: ranked.map(({ productId, fitScore, rank, components }) => ({ productId, fitScore, rank, components }))
};
```

Sort product IDs and component keys deterministically before JSON serialization. Hash with Node built-in crypto:

```js
import { createHash } from 'node:crypto';
const hash = createHash('sha256').update(JSON.stringify(canonical)).digest('hex');
```

Two runs with identical frozen inputs/version IDs must produce identical hashes.
